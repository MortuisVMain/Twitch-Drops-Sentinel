# Карта происхождения ядра Twitch-фарма

Дата: 2026-11-06. Статус: первичная карта происхождения и границ замены; реализация нового ядра не начата.

## Результат и границы

Ядро Twitch-фарма Sentinel является производной реализацией TwitchDropsMiner. Это прямо зафиксировано в [THIRD_PARTY_NOTICES.md](../THIRD_PARTY_NOTICES.md). Собственные изменения Sentinel не отменяют происхождение сохранённых частей.

Карта охватывает все 30 Python-файлов непосредственно в `core/`, группу из 21 JSON-файла `core/lang/` и основные границы подключения ядра. Она не является полным аудитом происхождения всех файлов репозитория, зависимостей или бинарной поставки.

Вторая заимствованная подсистема — `giveaways_engine/`: уведомление проекта относит её к free-games-claimer и указывает AGPL-3.0. Перепись Twitch-ядра сама по себе не делает весь Sentinel независимым от стороннего кода. Полный аудит этой подсистемы находится вне текущей карты.

**Этот документ содержит сведения, полученные при чтении старой реализации. Он предназначен для владельца проекта и проверяющего происхождение, а не является чистой спецификацией для изолированного разработчика нового ядра.** Для такого разработчика нужно отдельно подготовить требования к поведению и допустимые источники.

## Обозначения

| Метка | Что подтверждено | Чего метка не означает |
|---|---|---|
| D | Производный модуль: происхождение заявлено проектом, есть соответствующий модуль и подтверждённые различия реализации | Не означает, что каждая строка заимствована или что модуль неисправен |
| I | Текст совпадает с соответствующим файлом источника после нормализации переводов строк | Не означает уникальность кратких конструкций или побайтовое совпадение |
| A | Адаптер Sentinel с иной ролью по сравнению с исходным компонентом | Не доказывает независимое происхождение каждой строки |
| N | В корне проверенной версии TwitchDropsMiner нет одноимённого файла | Не исключает код из других файлов, проектов или источников |
| R | Группа ресурсов с соответствующей группой исходного проекта | Не устанавливает авторство каждой строки ресурса |

Решение «сохранить» ниже означает сохранить функцию или компонент при условии проверки происхождения. Оно не даёт права считать непроверенный код независимым. Решение «заменить» означает самостоятельно реализовать требуемое поведение, а не переформатировать старый файл.

## Подтверждённые смешанные участки

Граница подключения подтверждена в `core/sentinel_service.py`: импорт `Twitch`, `Settings`, `constants` и `utils` в районе строк 178–183, создание клиента около строки 1786. `desktop/MainForm.cs` находит и запускает Python-сервис в участке 885–1021. `desktop/TwitchDropsSentinel.csproj` встраивает `dist/index.html` (строка 38); это не доказательство состава всего релиза или отсутствия Python-файлов рядом с EXE.

Контекст локальной адаптации: [архитектура Sentinel](solutions/001-twitch-drops-sentinel-architecture.md) и [контракт headless GUI](solutions/002-headless-gui-contract-and-service-hardening.md). Эти записи поддерживают описание роли адаптеров, но не заменяют проверку происхождения каждой строки.

Эти примеры показывают, почему нельзя разделить происхождение по принципу «весь файл старый» или «весь файл наш».

1. **Просмотр:** `channel.py`, метод `send_watch`, сохраняет общий с исходным проектом механизм: получение HLS-плейлиста и HEAD-запросы к сегментам. Собственное имя приложения не меняет происхождение этой реализации.
2. **Авторизация:** в Sentinel выбран SMARTBOX и вход по коду устройства; проверенная версия исходного проекта использует ANDROID_APP и браузерный вход. Это подтверждённое различие, но не доказательство независимой реализации всего модуля авторизации.
3. **Восстановление и прогресс:** в `twitch.py` есть специфичные для Sentinel опрос прогресса каждые три цикла и проверки длительного отсутствия прогресса. Их пользовательский смысл нужно включить в будущие требования; происхождение конкретных строк оценивается отдельно.
4. **Получение наград:** `inventory.py` содержит дополнительную Android-попытку и допускает успех при некоторых пустых ответах. Новую спецификацию следует строить вокруг подтверждённого результата, а не воспроизводить спорное поведение только ради совместимости.
5. **Таймер:** в Sentinel остаются ранние выходы при нулевом изменении минут, удалённые в исходном проекте. Часть эффекта компенсируется обновлением headless-адаптера. Переписывать нужно наблюдаемое поведение целиком, а не переносить отдельно выбранный патч.

## Решение о периметре независимой реализации

**Реализовать заново:** модели кампаний и наград, интеграцию с Twitch, сеанс просмотра, обработку прогресса, получение наград, планировщик и необходимые вспомогательные механизмы производного ядра.

**Сохранить как требования, затем независимо реализовать:** приоритеты, восстановление после зависания, отсутствие ложного «получено», восстановление после перезапуска, корректную остановку и интеграцию с UI.

**Сохранить как внешние компоненты после проверки границ:** интерфейс, Windows-оболочку, локальный сервис, хранение настроек, уведомления и системные функции. При этом N не превращается автоматически в «авторство доказано».

**Исследовать отдельно:** происхождение N-файлов, точную историю изменения производных файлов, переводы, определения запросов, тесты, ресурсы и состав дистрибутива. При отсутствии достаточных доказательств либо самостоятельно реализовать необходимую часть, либо оставить её явно указанной сторонней зависимостью.

В переходный период старое ядро может оставаться доступным для отката. Это означает, что переходная поставка всё ещё содержит производный код. Изменять заявление о составе можно только по фактическому содержимому финального артефакта.

## Следующие действия и условия завершения

1. Уточнить историю производных файлов и 21 перевода: записать источники изменений и неизвестные участки. Завершение: для каждого элемента есть подтверждённый источник либо явно описанный пробел; изменение текста не считается доказательством независимого авторства.
2. Проверить происхождение N-файлов по доступной истории и источникам. Завершение: основание сохранения каждого компонента записано; отсутствие аналога не используется как единственное доказательство.
3. Выделить контракт нового ядра с сервисом и UI. Завершение: перечислены команды, события, состояния ошибок, настройки и правила миграции; внутренние классы старого ядра не выступают контрактом новой реализации.
4. Подготовить отдельную спецификацию поведения для независимого исполнителя. Завершение: она содержит сценарии и критерии приёмки, но не перенесённые функции, структуру классов, комментарии или тестовые реализации старого ядра.
5. Перед удалением старой зависимости проверить реальный состав релиза, включая резервный движок, переводы и вспомогательные файлы. Завершение: каждый включённый компонент имеет установленное происхождение и актуальные уведомления.

Эта карта не разрешает удаление файлов, изменение лицензий, запуск живого фарма или начало переписи. Она фиксирует результат этапа исследования и основу для следующего решения.
