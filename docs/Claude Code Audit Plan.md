## Этап A. Обновления и сохранность настроек

### C01 — Доверенный источник обновлений и область передачи токена — P1

**Где:** `core/sentinel_service.py`, handle_apply_update около 961; `core/updater.py`, apply_update_from_url около 283, заголовки около 324; cors_middleware около 559 в сервисе.

**Доказательство:** маршрут принимает download_url из тела запроса. Обновлятор добавляет Authorization к произвольному первоначальному HTTP(S)-адресу. В изолированном запуске заглушка получила Bearer SYNTHETIC_TOKEN для untrusted.example. SafeAuthRedirectHandler убирает заголовок при смене узла, но не защищает первоначальный запрос. Маршрут доступен на loopback без проверки авторизации; CORS разрешает любой Origin. Эксплуатация через конкретный браузер не проверялась.

**Работа:** получать/проверять допустимый артефакт по доверенным метаданным релиза заданного репозитория, а не доверять произвольной ссылке клиента. Проверять схему и разобранный hostname, а не подстроку URL; учесть цепочки перенаправлений. Передавать токен только там, где он нужен и адрес доверен. Спроектировать защиту изменяющих состояние локальных маршрутов с учётом реального WebView-origin и необходимых локальных клиентов; один CORS не является авторизацией. Сохранить поддержку легитимных GitHub asset redirects и сценария без токена.

**Приёмка:** чужой начальный URL и поддельный hostname отклоняются до загрузки/записи; redirect не уносит Authorization; валидный релиз устанавливается на искусственном стенде с токеном и без него. Неразрешённый локальный запрос не запускает установку. Реальный токен в тестах отсутствует. Отдельный security-review последнего diff.

### C02 — Нормализация защищённых путей архива — P1

**Где:** `core/updater.py`, цикл извлечения и PROTECTED_PATHS около 411–450.

**Доказательство:** blacklist проверяет исходное rel_path до resolve. Член архива `./config.json` проходит проверку и перезаписывает тот же защищённый файл. Временный искусственный конфиг был заменён; обновлятор вернул успех.

**Работа:** сначала нормализовать архивный путь и установить его допустимость относительно корня установки, затем сопоставлять с защищёнными путями/каталогами. Учесть регистр Windows, разделители, wrapper-directory и эквивалентные пути. Проверить отсутствие обходов через особенности Windows-путей и ссылки. Нельзя считать существующую проверку выхода за корень достаточной защитой пользовательских файлов внутри корня.

**Приёмка:** config.json, ./config.json и core/../config.json не меняют защищённый файл; то же для журналов и защищённых каталогов. Проверены обычный патч, wrapper-directory, выход за корень и Windows-варианты. Хеши всех искусственных пользовательских файлов до/после совпадают; обычные программные файлы обновляются.

### C03 — Корректный сброс и атомарное сохранение настроек — P1

**Где:** `core/sentinel_service.py`, handle_reset_settings около 1116, save_settings около 422; `core/settings.py`, default_settings около 32.

**Доказательство:** reset подставляет defaults движка, содержащие URL, set и enum, вместо схемы supervisor. Запись открывает config.json в режиме w перед json.dump. Изолированно получены TypeError для URL и обрезанный невалидный временный JSON. Маршрут зарегистрирован, текущий UI-вызов не найден.

**Работа:** выделить единый источник defaults supervisor для начальной загрузки и сброса. Сначала валидировать/сериализовать, затем атомарно заменять конфиг; ошибка записи должна доходить до вызывающего обработчика. Сохранять отдельную сериализацию настроек движка. Не сообщать успех при частичном сохранении; определить согласованное поведение памяти и диска при ошибке.

**Приёмка:** reset на фикстуре выдаёт валидную схему supervisor и согласованный ответ; повторная загрузка успешна. Ошибка сериализации/записи сохраняет прежний конфиг и возвращает ошибку. Ни один тест не вызывает reset живого сервиса.

Различать обязательные и необязательные файлы; не расширять бэкап на несвязанные секреты и данные. Формат должен позволять восстановить профиль, а не только создать ZIP.

**Приёмка:** архив искусственного профиля содержит supervisor-конфиг, необходимые настройки движка и согласованный набор данных. Два файла с одинаковым basename сохраняются без потери. Содержимое и пути проверены; отсутствие обязательного файла не выдаётся за полный успешный бэкап.

## Этап B. Соблюдение настроек и намерений пользователя

### C05 — Отмена уже начавшегося автовыключения — P1

**Где:** `core/sentinel_service.py`, luna_autoshutdown_loop около 1595–1624.

**Доказательство:** auto_shutdown_on_complete проверяется только при постановке отсчёта. Уже существующий luna_countdown тикает независимо. Изолированно при выключенной настройке и остатке 1 метод вызвал заглушку shutdown /s /t 0.

**Работа:** отменять ожидающее действие при отключении функции; повторно проверять завершённость и разрешение непосредственно перед системным вызовом. Проверить появление новых незавершённых целей/изменение очереди. Обновлять отображаемый отсчёт и журнал отмены согласованно. Сохранить существующие режимы, не добавляя новых действий питания.

**Приёмка:** выключение переключателя на любой секунде отменяет команду; изменение условий завершения отменяет её; при неизменных допустимых условиях происходит ровно один вызов. Проверки выключения, сна и времени — только через заглушки.

### C06 — Применение сохранённых флагов при каждом запуске движка — P1

**Где:** `core/sentinel_service.py`, run_twitch_engine около 1645–1660 и save_settings около 452; `core/twitch.py`, начальные claim_channel_points_enabled, auto_claim_drops_enabled, streamer_watchdog_enabled около 472.

**Доказательство:** Twitch создаёт три флага со значением True. Путь запуска переносит priority/exclude/mode, но не эти флаги. Их перенос есть только в обработке сохранения настроек. После перезапуска UI может показывать False, а движок работать с True.

**Работа:** применить persisted flags к каждому созданному клиенту до run(), включая автоматический перезапуск после ошибки. По возможности использовать один небольшой метод применения для старта и изменения настроек, без архитектурного рефакторинга.

**Приёмка:** для всех трёх выключенных флагов старт и восстановление движка сохраняют False; включённые значения также корректны; позднее переключение работает. Фиктивный Twitch-клиент фиксирует значения на входе в run().

### C07 — Частичные обновления настроек без возврата старых значений — P2

**Где:** `src/hooks/useSentinelState.ts`, handleUpdateSettings около 328; `src/components/SettingsStudio.tsx`, handleRemoveFolder около 216; серверный handle_update_settings.

**Доказательство:** удаление каталога обновляет локальный directories, но общий снимок настроек ещё старый до опроса/рескана. Быстрое переключение другой настройки отправляет весь merged snapshot, включая удалённую папку, и сервер сохраняет её обратно.

**Работа:** отправлять изменяемые поля, согласовать локальное обновление и обработку серверного ответа. Проверить аналогичные targeted handlers, которые посылают полный settings. Не превращать задачу в общую миграцию состояния. Ошибки HTTP должны быть различимы с успешным сохранением; осторожно с откатом, чтобы не затереть более новое действие.

**Приёмка:** удалить каталог и до следующего poll переключить модуль — каталог не восстанавливается. Задержанные ответы и два последовательных изменения разных полей не возвращают старые значения. Все запросы — на фикстуре.

## Этап C. Раздачи

### C08 — Правильный контракт SSE состояния — P2

**Где:** `src/components/GiveawaysView.tsx`, обработчик state около 160–164; `core/giveaways_controller.py`, stream около 523 и последующие публикации состояния.

**Доказательство:** событие содержит только runner: {state, pid, ...}. Клиент считает его полным GiveawaysStateResponse, делает setData(stateData), затем обращается к stateData.runner.state. Возникает скрытое исключение, но замена данных уже запланирована. Изолированное исполнение фактического callback подтвердило потерю stores/inventory и отсутствие обновления isClaiming. Следующий 5-секундный poll может маскировать дефект.

**Работа:** явно типизировать событие runner и объединять его с полным снимком. Корректно обработать событие до первого HTTP-ответа, running/aborting/завершение, reconnect и некорректный payload. Согласовать HTTP и SSE так, чтобы запоздалый ответ не ломал более свежее состояние. Не подавлять исключения молча.

**Приёмка:** после начального state, запуска, остановки и завершения магазина/коллекции/scheduler не теряются; isClaiming соответствует состоянию. Проверить HTTP→SSE и SSE→HTTP порядки, reconnect и повреждённое событие.

Связь с прежним UI-аудитом: первоначально отсутствие магазинов ошибочно трактовалось как отсутствие аккаунтов; после загрузки пять магазинов подключены и коллекция содержит 30 предметов. C08 — отдельный доказанный дефект. Нельзя утверждать без трассировки, что именно он вызвал наблюдавшийся тогда экран.

## Этап D. Особые сценарии диммера

Базовая работа диммера не опровергнута: два монитора и повторный опрос в живом UI были успешны. Ниже статически подтверждённые специальные пути; сначала воспроизвести на подменённых аппаратных вызовах. Не менять оборудование пользователя ради RED-теста.

### C10 — Явный опрос должен возвращать аппаратную яркость — P2

**Где:** `desktop/MainForm.cs`, GetHardwareMonitors, DDC-ветка около 3291 и WMI около 3364; SCAN_MONITORS около 1824; NotifyWebviewDimmerState около 3916.

**Доказательство:** полученное из оборудования значение заменяется старым _monitorBrightnessMap для известного ID. После изменения через OSD/другое приложение «Опрос» способен показать старое значение; сохранение базы тогда тоже некорректно.

**Работа:** отделить принудительное обновление от отображения оптимистического состояния во время записи. Учитывать незавершённые записи и отказ аппаратного чтения; не заменять ошибки чтения вымышленным успешным значением.

**Приёмка:** кэш 80%, аппаратное чтение 60% → явный опрос показывает 60%; сохранённая база 80% сама не меняется. Аналогично для WMI. Запоздалый ответ не откатывает более новую команду без определённого правила согласования.

### C11 — Независимое сглаживание команд разных мониторов — P2

**Где:** `desktop/MainForm.cs`, SetHardwareBrightnessDebounced около 3487–3503 и SET_BRIGHTNESS около 1754; `src/components/ScreenDimmerView.tsx`, сценарии около 487–501.

**Доказательство:** один CancellationTokenSource общий для всех monitorId. Новая команда отменяет предыдущую даже другому монитору. Сценарии посылают отдельные команды каждому экрану. Дефект зависит от прихода команд в окно 100 мс; не утверждать, что он всегда проявляется на этой машине.

**Работа:** дебаунс по monitorId либо пакетное применение последних значений всех затронутых мониторов. Определить порядок master и индивидуальных команд. Корректно освобождать CancellationTokenSource и сохранять сериализацию доступа к оборудованию.

**Приёмка:** A→80, B→70 с интервалом меньше 100 мс приводят к двум аппаратным записям; серия A→60→65→70 приводит к последнему значению A. Проверить master/individual и закрытие приложения с ожидающими командами. Использовать управляемое время и fake hardware.

### C12 — Сохранение исходного mute при повторном блэкауте — P2

**Где:** `desktop/MainForm.cs`, SetBlackout около 4016/4050/4086; обработчик таймера около 3595–3605.

**Доказательство:** первое включение с mute-on-blackout запоминает исходный звук и выключает его. Если активный таймер затем вызывает SetBlackout(true) повторно, _wasMutedBeforeBlackout перезаписывается уже выключенным состоянием. При выходе звук остаётся выключенным.

**Работа:** запоминать исходное состояние только при переходе из обычного режима в блэкаут; повторные команды и смена целевого монитора не должны его терять. Проверить завершение и исключения в lifecycle, сохранив исходно выключенный звук выключенным.

**Приёмка:** unmuted→blackout→повторный blackout→выход возвращает unmuted; изначальный muted остаётся muted. Воспроизвести последовательность ручного включения и таймера на заглушках аудио/окон.

5. Писать воспроизводящий тест до исправления; хранить регрессии в проекте. Изучить существующую инфраструктуру до запуска: `test_sentinel_suite.py` имеет подготовку sandbox на верхнем уровне, а `tools/test_updater_dry_run.py` обращается к credentials и внешней сети. Не импортировать/запускать их без проверки побочных эффектов и изоляции. Название dry_run не доказывает безопасность.
6. После последней правки выполнить релевантные регрессионные тесты, TypeScript --noEmit и frontend build при изменениях TS/React, C# build при изменениях оболочки. Сам build не доказывает аппаратное поведение. Зафиксировать точные команды, результаты и exit codes.
7. Итоговая проверка относится к последней интегрированной ревизии обоих планов. Сверить diff и сохранность чужих изменений; не подменять работающий exe/бандл без разрешения.
8. Отчёт по каждому C-ID: исправлено и чем проверено / не воспроизвелось с объяснением / отложено с причиной. Не писать «всё исправлено» по одним статическим проверкам. Нетривиальные решения документировать в docs/solutions по актуальной нумерации, архитектурные решения — в docs/adr только при их наличии.

## Что не входит в этот план

Общий редизайн, смена тем, перестановка очереди, реальный сбор/авторизация, выпуск релиза и исправление снятых выводов о неработающих мониторах/магазинах. Палитра, фокус справки, семантика FARM и повторный STATUS уже находятся в предыдущем UI-плане и здесь не дублируются.
