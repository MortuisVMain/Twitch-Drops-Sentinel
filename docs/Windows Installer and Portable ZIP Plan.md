# Единый план: Windows Installer и Portable ZIP

Дата: 2026-11-10. Проект: Twitch Drops Sentinel.
Статус: план реализации; реализация, установка и испытания не выполнены.
Авторизация текущей задачи: подготовить этот документ. Начало реализации и публикация согласуются отдельно.

## 1. Результат и границы первого выпуска

Пользователь скачивает Setup, устанавливает Sentinel без прав администратора, запускает его через ярлык, при необходимости переносит профиль из portable-версии, обновляет через новый Setup и удаляет программу с сохранением своих данных.

Из одной подготовленной релизной сборки выпускаются Setup и полноценный standalone portable ZIP. Существующий patch ZIP сохраняется для поддерживаемого сценария обновления; его пригодность для installed-режима должна быть явно установлена.

| В первом выпуске | После первого выпуска |
|---|---|
| Установка для текущего пользователя | Установка для всех пользователей |
| Русский и английский мастер, выбор папки, ярлыки | Дополнительное оформление мастера |
| Раздельное хранение программы и данных | Полностью тихое автоматическое обновление |
| Безопасный перенос portable-профиля | Управление несколькими installed-профилями |
| Обновление через Setup и проверка запуска | Расширенная автоматизация восстановления |
| Согласованная политика существующего updater | |
| Автозапуск по выбору пользователя | |
| Удаление с сохранением данных, диагностика | |

Первый выпуск не требует автоматического отката во всех ситуациях. Он требует проверенного восстановления, сохранности профиля и понятной ошибки. Необязательные функции не расширяют этот план без отдельного решения.

Статически проверены пути и назначение следующих файлов; перед правками сверить текущие версии и Git diff:

Работа установщика, перенос авторизации и восстановление после сбоя пока не проверены. Размер Setup заранее не обещается.

## 3. Архитектурный контракт

| Область | Решение |
|---|---|
| Инструмент | Inno Setup; зафиксировать используемую версию компилятора |
| Привилегии | Per-user, без повышения прав; `PrivilegesRequired=lowest` |
| Программа по умолчанию | `%LOCALAPPDATA%\Programs\Twitch Drops Sentinel` |
| Постоянные данные installed | `%LOCALAPPDATA%\Twitch Drops Sentinel` |
| Portable | Сохраняет данные рядом с программой; режим определяется явно |
| Выбор каталога | Разрешён доступный для записи каталог; отказ в доступе не обходится повышением прав |
| Идентичность установки | Постоянный `AppId`, не зависящий от версии; обновление использует зарегистрированную установку |
| Автозапуск | Выключен по умолчанию при первой установке; одна запись и общий механизм управления из Setup и приложения |
| Повторная установка | Сохраняет пользовательский выбор, включая автозапуск и расположение |
| Несколько копий | В первом выпуске один активный Sentinel; понятное сообщение при конфликте installed/portable |
| Удаление | Сохраняет профиль; очистка данных только отдельным явным выбором, по умолчанию выключенным |

Разделить пути ресурсов, постоянного профиля, кэша/логов и временного staging. C# и Python должны получать согласованные пути независимо от текущей рабочей директории. Переиспользовать существующие функции; не создавать универсальный framework настроек.

Способ явного определения portable-режима выбрать после проверки всех точек запуска. Обеспечить совместимость старых portable-копий: появление нового маркера не должно молча перемещать или игнорировать их профиль.

`AppMutex` обнаруживает работающую программу, но сам её не закрывает. Согласовать реальное имя mutex, закрытие оболочки, сохранение состояния и завершение backend. Принудительное завершение не считать штатным успешным сохранением.

## 4. Порядок реализации и контрольные точки

Зависимости: этап 0 → 1 → 2 → 3 → 4 → 5 → 6 → 7. Документация и сбор проверочных свидетельств обновляются в соответствующем этапе.

### Этап 0. Инвентаризация и утверждение контракта

- Проверить Git status и локальные инструкции, сохранить чужие изменения.
- Составить карту всех записываемых данных: конфигурация, cookies/токены, история, настройки окна, WebView2-профиль, логи, кэш, engine state, staging и резервные копии.
- Для каждой записи указать владельца, путь в двух режимах, чувствительность, переносимость, сохранение/удаление и миграцию формата.
- Проверить зависимости Python, .NET и WebView2 и способ их доставки; определить поддерживаемые Windows и архитектуры по реальной сборке.
- Выбрать источник версии, способ определения режима, правила восстановления и доверия к пакету.
- Зафиксировать решения в новом ADR с доступным номером. Решения по платному сертификату и доступам вынести явно; секреты не включать в документ.

Готово: карта покрывает все обнаруженные операции записи и точки запуска; отсутствуют неопределённые владельцы данных и конкурирующие правила путей. Выполнена критика по трём направлениям: сбои/безопасность, простота, Windows-совместимость.

### Этап 1. Ранняя сквозная техническая проба

- Взять чистую релизную сборку из существующего процесса.
- Подготовить минимальный Setup и в изолированной VM пройти установку → запуск → закрытие → удаление на пустом тестовом профиле.
- Проверить автономность runtime, иконку, загрузку frontend/backend и WebView2.
- Сохранить список найденных зависимостей и ограничений. Пробная сборка не публикуется.

Готово: получены журналы компиляции и запуска, понятны недостающие зависимости. Успех этой пробы не означает готовность переноса, защиты данных или обновления; текущие app-local записи допустимы только в изолированной пробе.

### Этап 2. Разделение путей и совместимость portable

- Реализовать архитектурный контракт в обнаруженных Python/C# точках записи и запуска.
- Отделить ресурсы от профиля, staging и временных данных.
- Обеспечить создание чистых настроек при первом запуске. Рабочие конфиги разработчика не являются шаблонами.
- Для изменяемых форматов определить версию схемы, миграции и резервную копию перед преобразованием.
- При неподдерживаемой более новой схеме показать ошибку; не сбрасывать и не перезаписывать настройки.

Готово: тесты на временных каталогах проверяют оба режима, старый portable, запуск из другой рабочей директории, пробелы и кириллицу. Installed не пишет пользовательское состояние в папку программы. Тесты миграций сохраняют исходные данные при ошибке.

### Этап 3. Перенос portable-профиля

- При первом запуске installed предложить выбрать исходную папку либо начать с чистого профиля.
- Переносить только известные данные по явному списку; исходная папка остаётся неизменной.
- Выполнять перенос при закрытой исходной копии; не смешивать автоматически два существующих профиля.
- При конфликте предложить отмену/чистый запуск либо явно выбранное восстановление с резервной копией целевого профиля.
- Копировать во временное место, проверять результат и отмечать завершение только после успешного применения. Повтор после прерывания безопасен.
- Отдельно проверить переносимость авторизации: шифрование Windows, привязку WebView2 и сессий. Копирование файлов не считать доказательством сохранения входа.
- При невозможности восстановить вход сохранить остальные данные и предложить повторную авторизацию.

Готово: тестируются первый и повторный перенос, занятый источник, существующий профиль, повреждённый конфиг и прерывание. Хеши исходных файлов не изменяются; логи не содержат секретов. Авторизация имеет отдельный подтверждённый результат или явно указанное ограничение.

### Этап 4. Полный установщик и удаление

Предлагаемые новые файлы: `installer/sentinel_setup.iss` и скрипт сборки в `tools/`; окончательное имя скрипта согласовать с существующими соглашениями.

- Подавать на вход чистую подготовленную релизную папку, не корень рабочего репозитория. Использовать единый набор payload для Setup и standalone ZIP.
- Добавить русский/английский интерфейс, выбор папки, меню «Пуск», опциональный ярлык рабочего стола и запуск после завершения.
- Реализовать автозапуск через тот же механизм, что использует приложение; галочка должна иметь реальное действие и сохранять выбор при обновлении.
- Добавить постоянный AppId, версию, издателя, иконку, uninstall-регистрацию и корректную архитектуру пакета.
- Подключить проверенное завершение Sentinel перед заменой файлов; при отказе/таймауте выдавать понятный результат.
- Составить список принадлежащих установке файлов, ярлыков и записей. Удалять только принадлежащие ей объекты; сохранять неизвестные файлы и чужие portable-копии.
- Профиль сохраняется по умолчанию. Явная очистка ограничивается конкретным профилем и проверенным абсолютным путём, не следует за ссылками в другие каталоги.
- Предотвратить случайную установку поверх portable-каталога; направить пользователя к отдельной установке и переносу данных.

Готово: ISCC завершает сборку с кодом 0; проверка состава подтверждает runtime и отсутствие реальных конфигов, cookies, токенов, истории и логов. Установка, ярлыки, автозапуск, повторная установка и удаление проходят проверку в VM. `onlyifdoesntexist` не используется как единственная защита данных при удалении.

### Этап 5. Обновление, блокировка операций и восстановление

- Первый поддерживаемый installed-сценарий — установка новой версии через Setup.
- Определить политику внутреннего updater: подтвердить совместимость либо явно отключить применение обновлений в installed-режиме с указанием способа обновления. Portable сохраняет проверенный прежний сценарий.
- Согласовать Setup, updater и миграцию профиля через общую блокировку операций. Mutex единственного экземпляра и блокировка обновления имеют разные назначения.
- Обеспечить восстановление после аварии без вечного состояния «операция выполняется»; не снимать блокировку живого владельца по одному лишь таймауту.
- Проверять пакет и доступное место до замены, учитывать объём staging и резервной копии. Путь назначения берётся из идентичности конкретной установки.
- Переиспользовать пригодные части staged EXE swap; определить поведение для прерывания, блокировки файлов, перезагрузки и повторной попытки.
- Удалять устаревшие программные файлы только по списку принадлежности; не трогать профиль и неизвестные пользовательские файлы.
- Проверять происхождение пакета до замены: документировать доверенную цепочку доставки/подпись. SHA-256 служит проверке целостности, но сам по себе не удостоверяет издателя.
- Решить вопрос Authenticode и защищённого хранения ключей. Покупка сертификата и публичная публикация требуют отдельной авторизации. При отсутствии подписи фиксировать ограничение; автоматическое применение недоверенного пакета не разрешать.
- После обновления проверить запуск оболочки, доступность backend, совместимость версий и чтение профиля без запуска фарма, claims или других действий аккаунта.
- Для неуспешного запуска сохранить журнал и дать проверенный способ восстановления. Откат учитывать вместе со схемой данных; неподдерживаемое понижение блокировать до изменения файлов.

Готово: переход N → N+1 и переустановка той же версии сохраняют тестовый профиль; две параллельные операции не меняют файлы одновременно; повреждённый пакет отклоняется до замены; неработающая сборка не отмечается как успешно запущенная. Восстановление после сбоя проверено, а не только описано.

### Этап 6. Диагностика и полная приёмка

- Вести журнал стадий, версий, кодов ошибок и результата восстановления; предусмотреть открытие/экспорт отчёта.
- Исключить секреты и содержимое профиля; проверять отчёты синтетическими токенами-маркерами. Редактировать чувствительные сведения до экспорта.
- Проверки установки выполнять в чистой Windows VM/Sandbox без среды разработки; перезагрузку и вход в Windows — в среде, которая реально поддерживает эти сценарии.
- Использовать синтетические аккаунтные данные, mock network/OS/hardware для отказов. Не запускать на рабочем компьютере реальные обновления, claims, shutdown/sleep или запись аппаратных настроек.
- Перед запуском существующих тестов читать их побочные эффекты: название dry-run само по себе не гарантирует изоляцию.

Готово: обязательная матрица ниже пройдена после последних изменений; сохранены команды, exit codes, журналы и результаты UI-проверок. Недоступная VM, неподтверждённый перенос сессий или непроверенное восстановление отмечаются как ограничения, а не как успех.

| A18 | Экспорт диагностики | Причина тестового сбоя видна; токены-маркеры и cookies отсутствуют |
| A19 | Недоступна сеть при первом запуске | Поведение зависимостей соответствует заявленной offline/online модели |

Каждая проверка имеет запись: revision/версия артефакта, окружение, команда или UI-шаги, ожидаемый и фактический результат, exit code для команд, путь к журналу. После материального изменения повторяются затронутые проверки. Успех компиляции не заменяет runtime-проверку.

## 6. Организация работы и критический обзор

- Primary ведёт контракт, зависимости и итоговую приёмку. Максимум один активный субагент, последовательные ограниченные задачи.
- Luna: поиск и карта кода; Sol: реализация и тесты; Terra: Windows UI; Astra: архитектурная оценка и финальная проверка по необходимости, без рутинного кодинга и широкого поиска.
- Каждому исполнителю передаются конкретные файлы/владение, разрешённые действия, ограничения данных и критерий завершения; чужие правки сохраняются. Возврат — краткий отчёт до 150 слов с файлами и результатами.
- Перед изменениями в Python/C#/Windows загружаются соответствующие навыки. Изменения кода проходят обязательное профильное ревью; ревьюер запускается после завершения предыдущего исполнителя.
- Тесты воспроизведения для выявленных дефектов пишутся до исправления. Проверки путей, миграции и сбоев используют временные каталоги и моки. После последней правки выполняется релевантная проверка с анализом вывода и кода возврата.
- В критическом обзоре проверять: потерю данных и гонки; возможность уменьшить объём решения; требования Windows, runtime и обновления. Каждое замечание связано с конкретным сценарием и проверкой.
- Все новые текстовые файлы — UTF-8 без BOM; конфиги перед правкой резервируются. Никаких широких удалений каталога установки или профиля.

## 7. Условие завершения

Первый выпуск готов к публикации только после выполнения этапов 0–7, прохождения A01–A19 и закрытия замечаний, влияющих на сохранность данных, запуск, обновление и удаление. Неподдерживаемые сценарии явно ограничены в поведении продукта и инструкции. Полностью тихое обновление и all-users установка не являются условиями этого выпуска.

Следующее действие после согласования реализации: этап 0 — карта данных/зависимостей и ADR, затем изолированная сквозная проба. Создание этого плана не запускает реализацию автоматически.
