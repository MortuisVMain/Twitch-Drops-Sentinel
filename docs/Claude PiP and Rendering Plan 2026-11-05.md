# Claude: восстановление PiP, чёткость и компоновка Sentinel 3.5.9

Дата: 2026-11-05. Задача пользователя: мини-окно снова отображается плохо, текст/окна/фоны выглядят низкого разрешения; проверить приложение и подготовить план. Это план реализации, код приложения в ходе аудита не изменялся.

## 1. Подтверждённые наблюдения

Аудит выполнен на запущенном `TwitchDropsSentinel.exe` из корня проекта. Версия в интерфейсе 3.5.9. Проверены переходы Дашборд → Полка → Раздачи → Диммер → Настройки, плитки/список полки, меню оформления, вкладки темы/фона и Ctrl+M туда/обратно. Фарм и аппаратные настройки не переключались. Плиточное представление восстановлено после проверки.

- **PiP: нижние кнопки обрезаны.** Из обычного большого окна нажать Ctrl+M. Полученное окно на снимке 560×210: нижняя строка «Поверх / Узел / След. / Игнор» касается края и частично исчезает. Воспроизведено при тексте 90%, игре AION 2, длинном названии награды. Возврат Ctrl+M работает. Многомониторное перетаскивание ещё не проверено.
- **Настройка текста — 90%.** Мелкие подписи видны на всех экранах. Это фактор читаемости, но не доказательство неверного DPI или размытия всей поверхности WebView. Изображение, уменьшенное инструментом просмотра, нельзя использовать как измеритель резкости физических пикселей.
- **Тема Titanium, фон «Глобус», яркость фона 85%.** Фактура фона заметно просвечивает через рабочие панели, особенно в списке полки и диммере; визуально конкурирует с мелкими подписями.
- **Широкое окно плохо использует пространство.** В Раздачах названия коллекции обрезаются в узких карточках при большой пустой нижней части. В списке полки название слева, статусы и действия далеко справа, между ними огромный пустой участок. В Настройках и Диммере элементы небольшие, нижняя половина преимущественно декоративная.
- **Полка перегружена повторяющимися действиями.** На каждой обложке «Исключить», ниже несколько кнопок очереди и приоритета; полезная информация и изображения конкурируют с управлением. Это предложение улучшения, не доказанный функциональный дефект.

Не проверены: другие DPI/мониторы, 4K, 100/130% текста, светлые темы, работа всех команд палитры и модалок. Измерения GPU и резкости не выполнялись. Скриншоты доступны в истории аудита, отдельные PNG не сохранялись.

## 2. Опорные места кода

- `desktop/MainForm.cs`: около 1934 — вход в PiP; 2605–2623 — WM_DPICHANGED; 2761–2769 — коррекция размера после перемещения. Текущий целевой размер 560×210 DIP повторён в нескольких ветках. Проверить также ограничения WM_GETMINMAXINFO, MinimumSize, восстановление Bounds и состояние максимизации.
- `src/index.css:510–712`: PiP ограничен 100vh с overflow:hidden; шапка 34px, внешние отступы 8px, обложка 100px, HUD и нижняя панель имеют свои отступы/интервалы; кнопки заданы высотой 27px. Проверить вычисленные min-height, flex minimum и каскад общих tactile-btn/console-header, а не только явный height.
- `src/App.tsx:1441–1654`: PiP HUD, название награды, кольцо, действия. Бегущая строка постоянно анимируется через `.scrolling`; оценить поведение длинных и коротких названий.
- `desktop/app.manifest:19`, `desktop/Program.cs:74`: PerMonitorV2 и ApplicationConfiguration.Initialize уже присутствуют. Не добавлять повторно DPI awareness как предполагаемое универсальное исправление.
- `src/components/PhotoBackdrop.tsx:128`: drawing buffer зависит от clientWidth/clientHeight и min(devicePixelRatio, maxDpr). Для основного фона передаётся предел 1.5 (около 244). Это ограничивает детализацию при DPR > 1.5; при DPR 1 оно не объясняет проблему.
- `docs/solutions/036-pip-multi-dpi-drag-resilience-and-game-box-art.md` описывает прежние 560×275, поэтому его размеры устарели относительно кода. `056-readability-type-scale.md` описывает rem-шкалу и масштаб 70–130%. `058-comfyui-photo-backdrops.md` описывает исходники 2560px и превью 640px; фактические размеры загруженных файлов ещё измерить.
- Ранее подготовленный `docs/Claude UI Audit Plan.md` сохранить. Его замечания о клавиатуре/модалках повторно проверить на текущей версии; не считать их автоматически открытыми дефектами 3.5.9.

## 3. Порядок реализации

### P1 — сначала PiP

1. Воспроизвести дефект на текущем EXE и изолированной UI-фикстуре. Записать host client area, viewport, DPR, text scale, фактические bounding rect шапки/HUD/кнопок. Создать проверку, падающую именно из-за выхода кнопок за viewport.
2. Согласовать нативную высоту с реальным бюджетом содержимого. Начальная гипотеза — сумма шапки, обложки, панели действий и отступов не помещается в 210px, а overflow:hidden скрывает остаток. Подтвердить измерением; не выдавать простой возврат 275 за окончательное решение без проверки.
3. Выбрать минимальную устойчивую компоновку: ясные название игры/награды, процент и оставшееся время; полноценный возврат в окно; доступные действия. Убрать дублирование прогресса, если оно мешает размещению. Для кнопок соблюдать студийный контракт области нажатия 48×48 CSS px — увеличить окно/перекомпоновать действия вместо сжатия шрифта.
4. Свести целевые размеры к одному месту в host, чтобы вход, DPI-переход и WM_EXITSIZEMOVE не возвращали старую высоту. Не добавлять циклический обмен resize между React и C# без необходимости. При адаптивной высоте ограничить размеры рабочей областью монитора.
5. Название: статичное усечение с доступным полным текстом либо движение только при реальном переполнении; учитывать reduced motion. Не маскировать недостающую высоту скроллом всей мини-панели.

Приёмка: все кнопки полностью видны и доступны; ничего не перекрывает текст; 10 циклов обычное окно ↔ PiP не накапливают смещение/размер; возвращаются исходные bounds и состояние максимизации; перенос между реально доступными мониторами не вызывает скачков. Проверить RU/EN, 90/100/130% текста, короткое/длинное название, активный фарм/ожидание/пауза на фикстуре. Недоступные DPI-сценарии отметить явно.

### P1 — разделить мелкий текст и низкую чёткость

1. До изменений записать DeviceDpi/GetDpiForWindow, физическую клиентскую область, WebView ZoomFactor, JS devicePixelRatio/innerWidth/innerHeight, вычисленный font-size/line-height и загрузку Inter. Проверить актуальность dist и реально загруженной сборки. Не выводить токены или профиль пользователя в диагностику.
2. Снять сравнение одной сцены при 90%, 100%, 115%, 130% текста; оценивать нативные снимки 1:1. Проверить границы, SVG-иконки и текст раздельно. Найти глобальные zoom/transform/filter на предках текста, если они есть; исправлять только доказанный источник размытия.
3. Определить комфортную иерархию: основной текст ориентировочно 14–16px при 100%, вторичный не ниже 12px, поля ввода ≥16px. Увеличение текста должно сопровождаться переносами и изменением сетки, а не новым clipping. Сохранённые 90% пользователя не сбрасывать молча.

Приёмка: документирована причина каждого исправления; текст и границы чёткие при нативном просмотре; нет глобального растягивания готового растра UI; отсутствуют непреднамеренные обрезания на минимальном и большом окне. Увеличение DPR фонового canvas не считать исправлением DOM-текста.

### P2 — качество фонов и поверхностей

1. Измерить для «Глобуса» URL и naturalWidth/Height источника, размер текстуры/drawing buffer, client size и DPR. Убедиться, что основной фон не получает файл из каталога превью. Сравнить исходник → статичное изображение → шейдер на одном размере.
2. Если drawing buffer недостаточен, подобрать предел DPR по измеренному качеству и стоимости; не форсировать 4K/8K для всех окон. Если недостаточен сам исходник, исправить ресурс; искусственная резкость не восстанавливает детали. Учесть cover/crop и mip/bloom, прежде чем менять shader.
3. Сделать рабочие поверхности достаточно непрозрачными: фон остаётся декоративным, фактура не проходит через текстовые строки с той же силой, что через свободные области. Сохранить Titanium и остальные темы, не проводить массовый редизайн.
4. Сравнить GPU/frame time и память до/после на той же сцене. Проверить освобождение контекстов при смене фона и отсутствие лишней анимации в скрытом/свёрнутом приложении.

Приёмка: качество подтверждено снимками 1:1 и размерами буфера/источника; контраст обычного текста ≥4.5:1 на фактических поверхностях; нет утечек при повторном переключении фонов. Режим качества добавлять только если один разумный вариант не покрывает реальные устройства.

### P2 — улучшения после стабилизации

- Раздачи: увеличить полезную ширину названий, разрешить две строки; сделать второстепенные даты менее заметными. Сетка должна использовать доступное место без чрезмерной плотности.
- Полка, список: сгруппировать название/прогресс/статусы ближе; использовать устойчивые колонки вместо разнесения по краям широкого экрана.
- Полка, плитки: сохранить одно очевидное основное действие, второстепенные поместить в доступное меню; «Исключить» не должен перекрывать каждую обложку как главное действие. Ничего не скрывать исключительно за hover.
- Дашборд: активная цель и оставшееся время должны читаться раньше журнала. Журнал сохранить, но пересмотреть долю высоты и визуальный вес.
- Диммер/Настройки: расширить области нажатия, улучшить группировку; не растягивать панели только ради заполнения пустоты. Сохранить аппаратную логику, фоновые службы и поведение фарма.

Каждое улучшение принять отдельно по сравнению до/после; не блокировать исправление PiP большим редизайном.

## 4. Проверка и передача

Использовать существующие `tools/ui_fixture.js`, `tools/build_ui_harness.mjs`, `tools/check_overflow.js`, `tools/check_contrast.py`; сначала прочитать способы запуска. Дополнить проверку переполнений PiP-сценарием: прежняя матрица основных экранов из решения 056 не доказывает корректность PiP.

После последних изменений выполнить релевантные регрессионные проверки, `npm run build`; при изменении C# — сборку `desktop/TwitchDropsSentinel.csproj`. Проверить вывод и exit code. Затем проверить именно новый EXE с соответствующим dist: один успешный build не доказывает исправление живого окна. Не подменять запущенный пользовательский EXE без согласованного перезапуска и сохранения данных.

Триада перед патчем: скептик проверяет DPI/resize-петли и сохранение bounds; прагматик исключает новый масштабный framework и несвязанный рефакторинг; UI/Windows-специалист проверяет CSS px против физических пикселей и реальные hit targets. Конфиги перед изменением резервировать, файлы писать UTF-8 без BOM. Имеющиеся изменения LICENSE, core/lang/English.json и предыдущие планы не перезаписывать.

Отчёт Claude: изменённые файлы → подтверждённая причина → выполненные проверки и exit codes → сравнение до/после → непроверенные сценарии. После подтверждённого исправления описать новую причину регрессии в docs/solutions и отметить устаревшие размеры из 036, сохранив историю.
